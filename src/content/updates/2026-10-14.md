A long day across ordering, approvals and the agents. The clearest difference is at the front of the product: two flows that used to make you work around them now do the obvious thing.

## For our partners

1. Ordering a website audit is one form: who the audit is for, the Business Profile locations, the audit's inputs, and the order itself.
2. Creating a client for a website already on your books offers that client instead of making a second one.
3. A plan waiting on approval stays current. Edit it anywhere and the request is rebuilt from the live plan and sent again.
4. A task created by hand opens its approval request the moment it is created, both in the app and over the API, so it arrives with the rest of your approvals.
5. In the client portal, tasks assigned to the client are marked For you, lead the list, and are counted in the sidebar and the header. Blocked work reads On hold.

### 1. One form for an audit order

Ordering an audit used to cross four screens: the packages card, a two-step new client form, a dialog that re-confirmed the package, then the order form. It is one form now. Pick the package, give the website, business name and brand (or start from an existing client's Project Work page), search for the Business Profile locations the local grid should be scanned from, pick the place rankings are checked from, and order.

Two things are clearer than they were. Without a Business Profile the audit has no local section, and the form says so where you choose. The local search term is yours to set rather than something the system picks for you. If you would rather we set the ranking location and the local search, a switch hands that to our team, and your project page says we are setting it up.

### 2. The client you already have

If the website you are entering already belongs to one of your clients, the form stops and offers the choices that make sense: launch from the discovery already sitting there, open that client, or create a separate client on purpose. Franchise micro-sites that live on one domain under different paths stay separate clients. A `www.`, a trailing slash, casing or a query string never splits one site in two.

### 3. Plans stay current while they wait

Add an item, retitle the plan, reword an item, cancel one or remove one, from the app or over the API, and the open approval request is rebuilt from the plan as it now stands. The share link and the review page show the current list, the request's history records what changed, and you are asked again, as is your client when the review goes to them.

## Behind the scenes

An agent's work is now tied to the website it is about, with the SEO service attached when there is one, so an agent can work on a website that never bought ongoing SEO. Each piece of work stands on its own instead of draining through a single line per client, and whether an agent's work waits for other work is a property of that agent. The agent that reads your notes and drafts a reply no longer sits behind a planner.

The bigger piece was answering one question once. Whether a given agent applies to a given client was decided in a dozen different places, each with its own copy of the rule, and the copies had drifted: the schedule honoured a condition that the screen listing scheduled agents ignored, and starting an agent by hand asked nothing at all. There is one answer now, with three ways in that differ exactly where we decided they should, and a refusal written in plain words when an agent does not apply. Who an agent is for lives on the agent itself rather than being restated inside each trigger, and the editor offers only the conditions that make sense for the kind of agent in front of you.

We also built the page our team reviews agent output from, shaped per kind of agent rather than one table for all of them. Each row names the website, opens a card saying what woke the agent and where it worked, opens a task over the page instead of sending you away from it, and carries a reviewed mark. It used to take a minute to load. It opens now.

One precision fix worth naming: the planner reads only the commitments belonging to the service it is working for, so pages bought once as a project no longer read to it as a monthly promise.
