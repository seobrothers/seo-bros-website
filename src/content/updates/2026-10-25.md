Most of today sat in Listings, with a second thread on what a partner can do over the API without opening the app.

## For our partners

1. A location's Listings page has a Download client hand-off button: a file of what the practice has to finish, with the logins it needs.
2. When two pages describe the same location, the one we hold or are already correcting stays the listing.
3. The Listings page shows its counts and quick filters for every partner, marks a priority site with no listing as one that has to be created, says whether a listing links to the website with a dofollow link, and reads your agency's name as "your team".
4. Approvals, client questions and discoveries can be worked over the API: approve or send back, answer a question, set a retail price, mark a discovery won or lost, remove a plan item with a reason.

### 1. The client hand-off export

Three sections: the location record so the client can check it against their own, each item waiting on the practice with the steps and the login for that site, and every login on file. Items waiting on us stay out, because they are not the client's to do, and your own master accounts for a directory never appear. The steps are rewritten so they read as coming from your agency; our name is nowhere in the file. It is built when you press the button and stored nowhere. It holds passwords, so send it the way you would send passwords.

### 2. Which page stays the listing

The old ranking read only how accurate each page looked, which demoted the page we had claimed or sent a correction to, since it reads wrong precisely while the fix is in flight. Now a page we hold, have a login for, or have a correction moving on stays the listing, and a page we have asked a directory to remove is never kept as one. Accuracy, then age, decide the rest. Re-running it restores listings an earlier pass had folded away as duplicates.

### 4. Decisions over the API

Every ask carries its type, so you can pull just written content, just site edits, or just plans. Declining is for work we proposed and always carries a reason, because the reason is what stops the same idea being proposed again; content already agreed in the plan gets sent back with what to change instead. Removing a plan item has its own door and also needs a reason: a plan still waiting on you is asked again on the shorter list, an approved plan carries on.

## Behind the scenes

A day of real browser runs taught the agents that work directory listings three things. A contact form that only draws its captcha once you touch a field was being treated as a form with no captcha, and the site accepted the messages anyway, which is worse than refusing them. A button offering to text a code was being read as proof a code had been texted, so runs stopped waiting for a phone while the emailed code was already typed. And a section heading on a profile page was read as the business name, which queued a rename nobody wanted. All three are checked for now, and the work queue says up front which items cannot start, so nothing is attempted that would only be refused.

We also collapsed how requests to build something are recorded. One record now: a title, a paragraph, a longer write-up if it needs one, and tags for the parts of the product it touches. It is open, shipped or declined, and the work itself lives on the ticket rather than in a second copy of it. The API reference is generated from the same place the doors are defined, and the build now fails if a field a door reads is undocumented, so the document cannot quietly fall behind.
